### **Название задачи:**
Реализация просмотра истории заказов с требованиями к быстрому отклику

### **Проблема**

Компания NovaMarket сталкивается с необходимостью добавить функциональность просмотра истории заказов для покупателей.
Существующая архитектура использует одну операционную БД заказов, которая предназначена под запись (создание и обновление заказов). При росте нагрузки до 40 000+ заказов в день чтение истории из этой БД станет узким местом из-за сложных JOIN'ов между таблицами заказов, товаров, статусов, доставки и оплаты.

#### Логика принятия решения

Для реализации истории заказов был выбран паттерн **CQRS**.

**Основные принципы:**

1. **Разделение на команды (запись) и запросы (чтение)** — операции создания/обновления заказа идут в операционную БД, а запросы истории читают из аналитической БД
2. **Две БД внутри одного сервиса** — не выделяем отдельный микросервис, чтобы не усложнять архитектуру на начальном этапе
3. **Асинхронная синхронизация через Kafka** — при изменении заказа публикуется событие, которое обновляет аналитическую БД

**Почему выбран именно этот подход:**

- Операций чтения истории будет значительно больше, чем записи
- Денормализованная структура аналитической БД позволяет выполнять сложные запросы без JOIN'ов
- Разделение нагрузок позволяет масштабировать БД для чтения независимо
- При росте нагрузки можно легко вынести аналитическую часть в отдельный сервис

### **Описание работы**

1. **Создание заказа** — покупатель оформляет заказ, `order_service` сохраняет его в **операционную БД** (нормализованную) и публикует событие `OrderCreated` в Kafka
2. **Синхронизация** — `order_service` (в отдельном consumer) читает своё же событие из Kafka, собирает данные из связанных таблиц и формирует денормализованную запись
3. **Обновление истории** — consumer сохраняет или обновляет запись в **аналитической БД** (денормализованной), где все данные по заказу хранятся в одной строке
4. **Чтение истории** — покупатель запрашивает историю через `GET /api/orders/history`, `order_service` читает данные напрямую из аналитической БД без JOIN'ов
5. **Изменение статуса** — при любом изменении заказа (оплата, доставка, отмена) публикуется новое событие, которое аналогично обновляет аналитическую БД

**Итог:** запросы истории выполняются быстро (нет JOIN'ов), запись заказов не блокируется чтением, при росте нагрузки аналитическую БД можно масштабировать отдельно.

### Альтернативы

#### Альтернатива 1: Чтение истории напрямую из операционной БД

**Плюсы:**
- Простота реализации
- Нет задержки синхронизации

**Минусы:**
- Сложные запросы с JOIN'ами на больших объемах данных
- Высокая нагрузка на основную БД заказов
- Невозможность масштабировать чтение независимо от записи

#### Альтернатива 2: Выделение отдельного сервиса истории заказов

**Плюсы:**
- Полная независимость масштабирования
- Чёткое разделение ответственности

**Минусы:**
- Усложнение архитектуры (дополнительный сервис)
- Операционные затраты на поддержку
- Избыточно для текущих нагрузок

#### Альтернатива 3: Event Sourcing

**Плюсы:**
- Полная аудитория всех изменений
- Возможность восстановления состояния на любой момент времени

**Минусы:**
- Высокая сложность реализации
- Большое количество событий
- Сложность с изменениями структуры событий
